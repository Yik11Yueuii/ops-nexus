# OpsNexus 企业知识运营助手：精简产品需求文档

> 版本：v1.1（开发边界修订，2026 年 9 月 5 日）  
> 演示企业：虚构的“星云科技”  
> 汇报时间：2026 年 9 月 14 日上午  
> 功能冻结：2026 年 9 月 10 日；9 月 11～13 日仅测试、修复和准备汇报

## 1. 产品定位与目标

OpsNexus 面向星云科技的研发、测试、运维和技术支持人员，提供可追溯的企业技术知识问答、故障辅助诊断和知识治理能力。产品重点体现 AI 应用开发能力，并以 Java 后端工程能力保障权限、安全、数据、缓存、审计和可测试性。

本次只交付一个可本地启动、可稳定演示和可测试的单体系统闭环：

```text
文档入库 → 版本化知识库 → 可追溯问答 → 故障辅助诊断
                         ↘ 版本对比 / 知识缺口闭环
```

## 2. 用户与权限

| 角色 | 能力 |
|---|---|
| 普通用户 | 登录、查询已发布知识、故障诊断、查看历史会话、点赞/点踩 |
| 知识管理员 | 普通用户全部能力；知识库和文档管理、版本发布、版本对比、缺口处理、管理员数据分析 |

首版不实现复杂组织架构、多租户和细粒度数据权限。所有管理接口必须进行管理员权限校验；用户只能检索有权限且已发布的文档。

## 3. 功能范围

### 3.1 P0：核心必须完成

1. 登录与两级角色权限。
2. 知识库创建、编辑、查询和文档关联。
3. PDF、DOCX、Markdown、TXT 上传；解析、切分、Embedding、向量入库、删除和处理状态展示。
4. 文档主题、版本号、状态、生效时间和当前版本管理；检索只使用已发布且有效的版本，并优先当前版本。
5. RAG 问答：检索、答案生成、SSE 流式输出、多轮会话和会话持久化。
6. 基础向量检索和必要的版本、状态、知识库元数据过滤。
7. 可信回答：返回答案、可信等级、证据充分性、文档/版本/页码/原文片段引用；证据不足时明确拒答或提示补充资料。
8. 会话历史、用户反馈、AI 调用日志、Token 统计、基础请求限流、超时和基础异常提示。

以下为 P0 增强项，只在核心链路稳定后实现，不得阻塞首版验收：

- 向量与关键词结合的混合检索；
- AI 自动生成文档摘要和标签；
- Redis 不可用时的自动降级；
- 更完整的限流策略和治理统计页。

### 3.2 P1：必须完成的三个创新闭环及配套能力

#### A. 故障辅助诊断

用户输入服务、错误现象和上下文后，系统检索排障 SOP 与历史故障，并调用至少两个只读业务工具（服务信息、发布记录、故障记录中任选两个以上），输出结构化结果：

- 现象摘要；
- 建议排查步骤及顺序；
- 可能原因；
- 文档事实、工具结果、AI 建议三类来源区分；
- 风险提示和下一步行动。

首版只保证一个稳定演示场景，例如 `order-service` 的数据库连接超时或 Redis 连接池耗尽。

诊断结果附证据卡，展示实际参考的 SOP 版本、工具返回的服务版本和最近发布时间，以及工具查询时间。查询失败或字段缺失时明确标记，不补造数据。

#### B. 文档版本对比

管理员选择同一主题的两个版本，系统输出结构化的新增、删除、调整、配置/步骤变化、风险变化和冲突提示，并标出推荐使用版本。首版采用相关片段检索加模型结构化对比，不实现法律级逐字 Diff。

#### C. 知识缺口雷达

对无结果、低检索得分、证据不足、冲突回答和点踩问题形成缺口候选，按相似问题聚合并展示次数、优先级、最近时间、关联会话和处理状态。管理员可将缺口标记为处理中/已关闭；补充文档后可重新验证典型问题。

#### 配套能力

- 普通用户业务查询：仅使用后端预定义的只读 Tool Calling，例如查询服务当前版本，不允许模型或用户提交 SQL。
- 管理员智能数据分析：自然语言生成单条查询 SQL；权限校验、安全审核、只读执行和审计为必须项，生成 SQL、查询结果和基础自然语言结论必须展示。复杂图表、多轮数据追问和深度分析属于可选增强。
- 历史故障记录结构化抽取与相似案例推荐，范围限于演示数据。
- 检索过程可解释展示：命中文档、版本过滤、相关度、引用片段和最终可信等级。
- 固定问题集与基础问答评测。

## 4. 管理员 Text-to-SQL 安全要求

该能力只在管理员专页开放，采用独立的只读数据源和完整审计。参考指南中的字符串黑名单、分号检查和自动 LIMIT 仅作为原型启发，不能作为正式安全方案。

执行前必须依次完成：

1. 校验管理员身份和访问场景。
2. 仅向模型提供允许访问的表、字段及查询约束。
3. 使用 SQL 语法解析器生成 AST，不接受仅靠字符串前缀判断。
4. 只允许单条 `SELECT`；拒绝 DDL、DML、存储过程、子查询越权、危险函数和多语句。
5. 校验表名、字段名、函数和排序字段白名单。
6. 强制最大返回行数、查询超时和必要的资源限制。
7. 通过只读数据源执行，禁止使用具备写权限的连接。
8. 记录问题、生成 SQL、权限/语法校验结果、执行状态、耗时、返回行数和失败原因；不得记录密码、API Key 或不必要的敏感正文。

安全失败时不执行查询，并向管理员返回可理解的拒绝原因。H2 方言和最终业务表结构以实际实现为准，示例 SQL 不得直接照搬。

首版仅开放 `service_catalog`、`release_record`、`incident_record` 三张演示业务表及明确列出的字段。允许基础过滤、聚合、排序和最多两个白名单关联 JOIN；禁止系统表、CTE、UNION、子查询、笛卡尔积、存储过程和非白名单函数。不支持的语法拒绝执行，不自动放宽限制。

查询使用独立数据库账号，仅授予白名单表 SELECT 权限，不能只靠连接的只读标记；审计由业务数据源写入。最多返回 100 行，数据库查询超时为 3 秒；审计不可用时拒绝新查询。

Text-to-SQL 的最小完成范围为：管理员权限、结构化表信息提示、SQL AST 解析、单条 SELECT、表字段和函数白名单、只读执行、最大行数、查询超时、基础结果解读以及审计。可视化图表、复杂分析、多轮追问和自动修正 SQL 不属于本次必做范围。

## 5. 典型流程

### 5.1 文档入库

管理员上传 → 格式/大小/重复校验 → 解析正文与页码 → 生成摘要和标签 → 文本切分 → Embedding → 写入 SimpleVectorStore → 保存片段关联 → 发布版本 → 可检索。

处理过程必须有待处理、处理中、成功、失败状态；失败记录原因并支持重试。

首版文件约束如下：

- 单个文件最大 20 MB，每次请求只上传一个文件；
- 使用 SHA-256 校验值识别同一知识库中的重复文件；
- PDF 仅支持可提取文本的普通 PDF，不实现扫描件 OCR；
- 加密、损坏、空白或不支持的文件必须被拒绝并返回明确原因；
- 上传文件保存在本地受控目录，禁止使用原始文件名直接拼接存储路径。

文档版本分别记录处理状态和发布状态：

```text
处理：PENDING → PARSED（正文已解析，待向量化）→ PROCESSING → READY
                                                     └→ FAILED → PROCESSING（重试）
发布：DRAFT → PUBLISHED → ARCHIVED
```

只有处理成功、已发布且已生效的当前版本可作为普通问答依据。同一逻辑文档最多有一个当前发布版本；新版本发布和旧版本归档在一个数据库事务内完成。首版不实现预约发布，未来生效时间的版本须到期后手动发布。

检索候选在进入模型前必须按数据库中的知识库状态、当前版本和权限再次过滤；向量 metadata 不作为最终授权依据。向量需持久化并在重启后加载，失败重试和删除必须同步处理片段关联。历史引用可保留原回答证据快照，并提示版本已归档。

引用支持授权查看片段和下载原文件。PDF 显示真实页码，其他格式使用章节或片段编号，不伪造页码。

### 5.2 问答与诊断

用户提问 → 输入检查与会话读取 → 意图/路由 → RAG 或受控工具/诊断流程 → 证据校验 → 可信等级计算 → SSE 输出 → 保存消息、引用、日志和反馈 → 必要时登记知识缺口。

SSE 至少定义以下事件，前端不得依赖模型原始输出格式：

```text
start → delta（可重复）→ evidence → complete
                              └→ error
```

`complete` 事件统一返回消息 ID、可信等级、证据充分性、引用摘要和 Token 统计；`error` 返回稳定错误码和用户可理解的信息。

可信等级首版采用后端规则计算，不直接采用模型自评分：

- 高：去重后的有效证据与问题直接相关、满足高可信阈值和版本要求，且无已知冲突；引用数量不作为高可信的充分或必要条件；
- 中：至少存在一个有效引用，但证据覆盖不完整或只达到基础阈值；
- 低：没有有效引用、低于检索阈值、仅命中过期版本或存在未解决冲突。

具体数值阈值必须配置化，并通过固定测试问题集调整。低可信回答不得给出确定性的企业操作结论，应说明证据不足并建议补充资料或联系负责人。

页面同步解释证据充分性与降级原因，可信等级不代表经过统计验证的答案准确率；无法确认依据覆盖问题时不得判为高可信。

### 5.3 版本对比与缺口处理

管理员选择版本 → 获取两侧有效片段 → 模型输出结构化差异 → 展示冲突和推荐版本；低可信/未命中/点踩问题 → 语义聚合 → 管理员补充文档 → 重新验证 → 关闭缺口。

版本对比仅允许同一逻辑文档的两个版本，单次只比较两个版本，输出固定结构的新增、删除、调整、风险和冲突项。对于超长文档，可只比较筛选出的关键章节，但必须向用户说明实际覆盖范围。

知识缺口首版使用“问题文本规范化 + 向量相似度阈值”归并相似问题；达到阈值时增加已有缺口的出现次数，否则新建缺口。管理员可以手动合并、标记处理中和关闭，不实现独立的复杂自动分类模型。

缺口详情提供“重新验证”：以原问题在原知识库中重新检索，展示本次证据、版本、验证时间及新增引用。验证不增加缺口出现次数、不自动关闭；管理员确认后填写处理说明并关闭。未命中时保持待处理；特殊情况可填写原因人工关闭，不能标记为验证通过。

## 6. 页面与接口边界

首版页面仅保留：登录页、用户聊天页、会话历史、诊断结果页、知识库/文档管理页、版本对比页、知识缺口雷达页、管理员智能数据分析页。基础治理信息可以合并到管理员页面，不强制建设独立统计页。

后端按 `auth`、`knowledge`、`ingestion`、`retrieval`、`assistant`、`diagnosis`、`tool`、`analytics`、`conversation`、`gap`、`governance` 模块组织。接口统一返回成功/失败结构；流式问答使用 SSE。具体 URL 和字段在编码前以接口协议为准，但不得扩展到本 PRD 之外的业务系统。

## 7. 技术与数据约束

- 前端：Vue 3 + Vite + TypeScript。
- 后端：Java 21 + Spring Boot + Spring AI；模型使用已配置的云端模型，不接入 Ollama。
- 数据库：默认 H2 文件模式；额外提供 MySQL 配置；H2 保存核心业务和审计数据。
- 缓存/会话：使用本机 Redis；Redis 不可用时允许有限降级并明确提示。
- 向量存储：首版 SimpleVectorStore；通过抽象保留未来扩展，但不实现 PGvector。
- 文件：本地受控目录保存原始文档，数据库保存元数据和处理状态。
- 演示数据：全部使用虚构的星云科技及服务（如 `order-service`、`user-service`、`payment-service`、`api-gateway`）。

核心数据至少包括用户、知识库、文档、文档版本、文档片段关联、会话、消息、引用、反馈、知识缺口、服务目录、发布记录、故障记录、AI 调用日志和 SQL 审计。

H2 是本次开发、自动化测试和现场演示的唯一强制验收数据库。MySQL 只要求提供独立 Profile、配置示例和初始化方案，不要求在功能冻结前完成与 H2 同等级的全量兼容测试。

Redis 保存活跃会话上下文和短期计数，H2 保存可长期查看的会话与消息。若实现 Redis 降级，Redis 不可用时仅退化为当前进程的内存上下文与限流计数，历史消息仍以 H2 为准，不实现复杂缓存一致性协议。

## 8. 非目标与冻结边界

本次不实现：生产环境操作或高风险命令、完整工单/监控/CMDB、复杂多租户、海量数据与高并发 SLA、PGvector、MCP/外部系统接入、文生图、语音、翻译、Ollama，以及与核心演示无关的前置实验接口。

9 月 10 日后不得新增功能；只能修复缺陷、改善稳定性、补充测试数据和汇报材料。若时间不足，优先级依次为：P0 核心主链路 → 故障诊断 → 版本对比 → 知识缺口雷达 → Text-to-SQL 最小安全闭环 → 各类增强项。三个创新功能和 Text-to-SQL 安全底线均不得被展示增强挤占。

## 9. 验收标准

1. 按项目文档可在本机启动；前端、后端、H2 文件库和 Redis 的依赖状态可说明。
2. 管理员可上传四种格式文档，查看处理状态并发布版本。
3. 普通用户可针对已发布知识进行多轮 SSE 问答，并看到可点击引用、版本和可信等级。
4. 证据不足时系统不伪造企业事实，并能生成知识缺口候选。
5. 故障诊断在固定场景中同时使用 RAG 和至少两个只读工具，输出结构化排查清单。
6. 管理员可比较两个版本并看到结构化差异、冲突和推荐版本。
7. 点踩/低可信/未命中问题可聚合进入缺口雷达，并由管理员关闭。
8. 普通用户无法触发自由 SQL；管理员 Text-to-SQL 可展示 SQL、结果、结论和审计信息。
9. 越权表、非法字段、危险语句、多语句、超限结果和超时查询均被拒绝或中止，并留下审计记录。
10. 固定测试问题集覆盖权限、检索、引用、路由、工具安全、SQL 安全、降级和三个创新闭环；评价结构和关键事实，不断言不稳定的全文。
11. 发布新版本后旧版本不进入新回答；重启后向量可加载，失败重试不重复入库，引用可授权查看。
12. 缺口重新验证展示新增证据且不重复计数；诊断证据卡能区分实际查询结果和缺失信息。
13. 基础请求限流生效，SQL 查询账号不能写入业务表或读取非授权业务表，审计失败时禁止执行新查询。

每项功能只有同时满足以下条件才视为完成：

- 后端接口可运行，前端存在最小可用入口；
- 能使用星云科技固定数据完成一次端到端业务闭环；
- 至少覆盖一个正常场景和一个权限、参数或依赖异常场景；
- 失败时返回明确提示，不出现空白页、无限等待或未处理异常；
- 已纳入固定测试清单和演示脚本。

## 10. 演示主线

以星云科技 `order-service` 为主线：管理员上传部署手册 v1/v2 和故障 SOP → 普通用户询问数据库连接超时并获得带引用的答案 → 进入故障诊断，组合服务版本与历史故障工具 → 管理员比较两个部署手册版本 → 演示一次低可信问题进入知识缺口雷达 → 管理员查询“最近 30 天故障次数最多的服务”，展示安全审核后的 SQL、结果、结论和审计。

演示必须使用准备好的固定数据和问题，避免依赖临时上传、不可控模型输出或真实企业信息。
