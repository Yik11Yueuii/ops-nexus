## 1. 项目概述

### 1.1 项目名称

中文名称：**TechOps 企业知识运营助手**  
英文名称：**TechOps Knowledge Copilot**

### 1.2 项目定位

本项目面向中型软件企业的研发、测试、运维和技术支持团队，统一管理 API 文档、部署手册、排障 SOP、发布规范、历史故障复盘等内部资料，并基于 Spring AI 提供可追溯知识问答、故障辅助诊断、文档版本对比、企业工具调用和知识缺口发现能力。

项目不是单一的“上传文件后聊天”示例，而是前置 Spring AI 实验能力的综合应用。系统以 RAG 为基础，以智能路由和 Tool Calling 扩展业务能力，以可信回答、版本对比和知识缺口闭环形成项目特色。

### 1.3 一句话介绍

> 一个基于 Spring AI 构建的研发运维知识运营平台，让企业技术资料能够被检索、被解释、被执行，并在持续问答中发现需要补充的知识。

### 1.4 项目目标

1. 将前置 Spring AI 实验从孤立 Demo 整合为一条完整业务链路。
2. 建立从文档上传、解析、切分、向量化到 RAG 问答的完整知识处理流程。
3. 为回答提供文档、页码、原文片段、版本及可信度等可追溯依据。
4. 使用受控 Tool Calling 将普通用户问答扩展到服务、版本、发布和故障记录等业务数据查询。
5. 在管理员智能数据分析场景中提供安全受限的 Text-to-SQL，展示自然语言生成、审核、执行 SQL 及结果解读的完整链路。
6. 通过低可信回答、用户反馈和高频未命中问题发现知识缺口。
7. 做成学习型但完整可运行、可演示、可测试、可写入简历的小型项目。

### 1.5 非目标

初版不追求以下能力：

- 不直接连接或操作真实生产环境，不执行重启、发布、删除等高风险命令。
- 不实现复杂多租户、跨企业数据隔离和大型组织架构。
- 不承诺海量文档、高并发或生产级 SLA。
- 不实现完整工单系统、监控系统或 CMDB，只提供可替换的模拟查询工具。
- 不追求自主决策型 Agent；AI 只做辅助分析，关键结论需保留证据与人工判断。

## 2. 项目背景与业务问题

中型软件企业的技术知识通常分散在开发文档、Wiki、聊天记录、故障复盘和个人经验中，容易产生以下问题：

- 新员工不知道资料在哪里，重复询问资深同事。
- 文档存在多个版本，旧操作步骤可能误导使用者。
- 故障复盘完成后没有被有效复用，相似故障反复排查。
- 普通知识库只能搜索关键词，无法根据问题上下文组织答案。
- 普通 RAG 可能给出看似合理但证据不足的回答。
- 管理员不知道员工最缺少哪些知识，也无法量化文档价值。

TechOps 将“知识查询”和“知识治理”结合起来：员工获得有证据的答案，管理员通过反馈与未命中问题持续完善知识库。

## 3. 目标用户与权限

### 3.1 用户角色

| 角色 | 典型人员 | 核心诉求 | 初版权限 |
|---|---|---|---|
| 普通用户 | 研发、测试、运维、技术支持 | 问答、诊断、对比、查看历史 | 使用助手、浏览已发布文档、提交反馈 |
| 知识管理员 | 技术负责人、文档维护者 | 管理知识、处理缺口、控制版本、分析业务数据 | 知识库和文档管理、查看缺口与统计、使用智能数据分析 |
| 系统管理员 | 项目管理员 | 模型和系统配置 | 初版可与知识管理员合并 |

### 3.2 主要用户故事

- 作为研发工程师，我希望查询 API 和技术规范，并看到答案来自哪份文档。
- 作为运维工程师，我希望描述故障现象后获得有顺序、有依据的排查清单。
- 作为技术支持人员，我希望检索相似历史故障，快速形成客户问题处理建议。
- 作为知识管理员，我希望上传新版文档并了解它与旧版本的主要差异。
- 作为知识管理员，我希望知道哪些问题经常被问到但无法可靠回答。
- 作为知识管理员，我希望用自然语言查询允许访问的业务统计数据，并看到生成 SQL、查询结果和分析结论。

## 4. 核心业务场景

### 4.1 可追溯技术问答

用户提出技术问题，系统检索相关资料并流式生成回答，同时返回：

- 引用文档名称、文档版本和页码；
- 被采用的原文片段；
- 相关度或检索得分；
- 证据充分性和回答可信度；
- 文档是否已过期或存在冲突版本。

证据不足时，系统应明确说明“当前知识库没有足够依据”，不得把模型常识伪装成企业事实。

### 4.2 故障辅助诊断

用户输入服务名、错误现象和已知上下文，系统完成意图识别后：

1. 检索排障 SOP 和相似故障复盘；
2. 调用服务信息、发布记录、故障记录等只读工具；
3. 生成结构化排查步骤、可能原因和风险提示；
4. 区分“文档事实”“工具查询结果”和“AI 建议”；
5. 保存本次诊断会话，支持后续追问。

### 4.3 文档版本对比

管理员关联同一主题的两个文档版本，系统输出：

- 新增、删除和调整的主要内容；
- 配置项、操作步骤和风险提示的变化；
- 可能互相冲突的条款；
- 新旧版本状态及推荐使用版本。

初版采用“相关片段检索 + 大模型结构化对比”，不实现法律级逐字 Diff。

### 4.4 历史故障复用

系统将故障复盘抽取为统一结构，包括服务、现象、影响、根因、处理方案和预防措施。后续问题可以召回相似案例，而不是只检索大段原文。

### 4.5 知识缺口闭环

以下事件可形成知识缺口候选项：

- 检索无结果或最高得分低于阈值；
- 回答证据不足或发现文档冲突；
- 用户点踩回答；
- 同类问题被反复追问；
- 模型建议补充某类 SOP 或说明文档。

管理员可查看缺口排行榜、关联问题和处理状态，并在补充文档后关闭缺口。

### 4.6 分级数据库查询

系统按用户身份和业务场景提供两类相互隔离的数据库能力：

1. 普通用户业务查询采用受控 Tool Calling。模型只能调用后端预先定义的只读工具，例如 `queryCurrentVersion("order-service")`，不得生成或提交任意 SQL。
2. 管理员在“智能数据分析”专页使用安全受限的 Text-to-SQL。模型根据后端提供的白名单数据库结构生成一条查询语句，只有通过权限与 SQL 安全校验后才可由只读数据源执行，最后由模型对查询结果生成分析结论。

该设计完整保留案例 16 的自然语言生成并执行 SQL 能力，但不向普通用户开放自由 SQL，避免将实验能力直接暴露为通用数据库入口。

## 5. 产品创新点

### 5.1 可信回答协议

每次知识问答不只输出文本答案，还输出标准化的回答信息：

- `answer`：回答正文；
- `confidenceLevel`：高、中、低；
- `evidenceSufficiency`：充分、部分充分、不充分；
- `citations`：引用来源；
- `conflicts`：冲突或过期资料；
- `nextAction`：建议继续查询、补充资料或联系负责人。

可信度不是让模型凭感觉打分，而是综合检索得分、有效引用数量、版本状态和模型判断得到的可解释等级。初版使用规则计算，后续再评估模型评分。

### 5.2 知识缺口雷达

将“回答不了”转化为可管理的数据资产。管理端按出现次数、影响范围、负反馈数量和最近发生时间形成缺口优先级，体现从知识问答到知识运营的闭环。

### 5.3 文档版本与冲突感知

文档具有主题、版本、状态、生效时间等业务属性。检索时优先使用已发布且有效的最新版本，并提示旧版本或冲突内容，降低“检索正确但依据过期”的风险。

### 5.4 智能路由与多能力编排

系统先将用户请求结构化分类，再选择普通对话、RAG、工具查询、版本对比或故障诊断流程。通过统一路由把多个 Spring AI 实验能力组织成一个产品，而不是多个互不关联的接口。

### 5.5 可解释检索

系统可以展示检索关键词、命中文档、相关度、版本过滤结果和最终引用片段。这里展示的是业务证据与处理轨迹，不展示模型的内部思维链。

## 8. 核心用户流程

### 8.1 文档入库流程

```text
管理员上传文档
  → 校验格式、大小和重复文件
  → 解析正文与元数据
  → AI 生成摘要、主题、标签和结构化信息
  → 文本切分
  → Embedding 向量化
  → 写入向量库
  → 发布文档版本
  → 可被问答检索
```

### 8.2 智能问答流程

```text
用户提问
  → 输入检查与会话上下文读取
  → 意图识别/问题改写
  → 路由选择
      ├─ 普通对话
      ├─ RAG 知识问答
      ├─ Tool Calling 业务查询
      ├─ 故障辅助诊断
      └─ 文档版本对比
  → 证据校验与可信等级计算
  → SSE 流式回答
  → 保存消息、引用、Token 和反馈入口
  → 必要时登记知识缺口
```

### 8.3 知识缺口处理流程

```text
低可信/未命中/点踩问题
  → 按语义聚合相似问题
  → 计算缺口优先级
  → 管理员查看上下文
  → 上传或关联补充文档
  → 重新验证典型问题
  → 关闭知识缺口
```

### 8.4 管理员智能数据分析流程

```text
管理员输入自然语言问题
  → 校验管理员权限
  → 后端向模型提供允许访问的表、字段及查询约束
  → AI 生成单条 SELECT SQL
  → 后端解析并执行 SQL 安全审核
  → 校验表和字段白名单
  → 补充或收紧最大返回条数限制
  → 使用只读数据源执行并应用查询超时
  → 返回结构化查询结果
  → AI 根据问题和结果生成分析结论
  → 记录原始问题、生成 SQL、执行耗时和结果状态
```

例如，管理员询问“查询最近 30 天故障次数最多的三个服务”，模型可生成：

```sql
SELECT service_name, COUNT(*) AS incident_count
FROM incident_record
WHERE occurred_at >= CURRENT_DATE - INTERVAL 30 DAY
GROUP BY service_name
ORDER BY incident_count DESC
LIMIT 3;
```

示例 SQL 需根据 H2 实际方言和最终表结构调整后执行；模型输出不能绕过后端校验器直接访问数据库。

## 9. 技术架构初稿

### 9.1 总体方案

初版采用前后端分离的单体架构：

- 前端：Vue 3 + Vite + TypeScript；
- 后端：Java 21、Spring Boot 3.4.x、Spring AI 1.0.x、Spring AI Alibaba；
- 大模型：通义千问，默认 `qwen-plus`；
- Embedding：DashScope `text-embedding-v2`；
- 业务数据库：默认使用 H2 文件模式保证开箱即用，额外提供 MySQL 配置档；
- 缓存和会话：Redis；
- 向量存储：首版确认使用 SimpleVectorStore 持久化方案，通过接口隔离保留未来替换 PGvector 的能力，本次不实现 PGvector 配置；
- 文档解析：Spring AI PDF Reader、Tika Reader、Markdown Reader；
- 文件存储：本地受控目录，数据库只记录文件元数据。

选择单体架构是为了保证学习项目能够独立启动和完整演示。模块之间通过接口隔离，为后续替换数据库、向量库和模型保留扩展点。

### 9.2 后端模块建议

```text
auth              登录、权限和用户上下文
knowledge         知识库与文档生命周期
ingestion         解析、切分、Embedding、入库
retrieval         向量、关键词、混合检索和过滤
assistant         ChatClient、Prompt、路由和流式回答
diagnosis         故障诊断与排查清单
tool              服务、版本、发布、故障等只读工具
analytics         管理端 Text-to-SQL、SQL 安全校验、只读执行和结果解读
conversation      会话、消息、引用和反馈
gap               知识缺口聚合与处理
evaluation        测试集、问答评价和指标
governance        限流、日志、超时、降级和 Token
```

### 9.3 H2、Redis 与向量库职责

| 组件 | 保存内容 | 不保存内容 |
|---|---|---|
| H2 | 用户、知识库、文档元数据、版本、会话索引、消息、引用、反馈、缺口、服务和故障模拟数据 | 大文件正文、缓存数据 |
| Redis | 活跃会话记忆、热点问答缓存、短期路由结果、限流计数 | 需要长期审计的唯一数据 |
| VectorStore | 文档片段向量及检索 metadata | 用户权限主数据、完整业务状态 |
| 本地文件目录 | 上传的原始文档 | 用户和会话结构化数据 |

初版使用 H2 文件模式而非纯内存模式，确保项目重启后业务数据仍存在，同时通过 Spring Profile 额外提供 MySQL 的数据源与初始化配置。Redis 使用本机已安装环境；Redis 不可用时，系统应允许降级到内存会话或提示关闭会话持久化。SimpleVectorStore 不依赖单独部署向量数据库，适合本次本地开发和汇报；PGvector 仅作为未来扩展方向，不纳入 9 月 14 日前的交付范围。

## 11. 接口设计草案

### 11.1 认证与用户

- `POST /api/auth/login`：登录；
- `GET /api/users/me`：当前用户；
- `POST /api/auth/logout`：退出。

### 11.2 知识库与文档

- `GET /api/knowledge-bases`：知识库列表；
- `POST /api/knowledge-bases`：创建知识库；
- `GET /api/knowledge-bases/{id}`：知识库详情；
- `POST /api/knowledge-bases/{id}/documents`：上传文档；
- `GET /api/documents/{id}/versions`：文档版本列表；
- `POST /api/documents/{id}/versions`：上传新版本；
- `POST /api/document-versions/{id}/publish`：发布版本；
- `POST /api/documents/compare`：对比两个文档版本；
- `DELETE /api/document-versions/{id}`：删除未发布版本或执行受控下线。

### 11.3 助手与会话

- `POST /api/conversations`：创建会话；
- `GET /api/conversations`：我的会话列表；
- `GET /api/conversations/{id}/messages`：会话消息；
- `POST /api/assistant/chat`：非流式问答；
- `POST /api/assistant/chat/stream`：SSE 流式问答；
- `POST /api/assistant/diagnose`：故障辅助诊断；
- `POST /api/messages/{id}/feedback`：提交回答反馈。

### 11.4 缺口、评估与运营

- `GET /api/admin/knowledge-gaps`：知识缺口列表；
- `GET /api/admin/knowledge-gaps/{id}`：缺口详情；
- `POST /api/admin/knowledge-gaps/{id}/resolve`：关联文档并处理；
- `GET /api/admin/metrics/overview`：问答与调用概览；
- `POST /api/admin/evaluations/run`：运行基础问答评测。

### 11.5 管理员智能数据分析

- `POST /api/admin/data-analysis/query`：提交自然语言问题，生成并安全执行只读 SQL，返回 SQL、查询数据和分析结论；
- `GET /api/admin/data-analysis/history`：查询当前管理员的智能分析历史与执行状态；
- `GET /api/admin/data-analysis/schema`：返回可供分析的白名单表和字段说明，不暴露未授权数据库结构。

接口响应格式、错误码、SSE 事件协议和权限矩阵在 PRD 中细化。

## 13. 非功能性要求

### 13.1 安全

- API Key 仅从环境变量读取，不写入代码和仓库；
- 上传文件校验扩展名、MIME、大小和安全文件名；
- 普通用户的业务数据查询只允许调用预定义只读工具，禁止生成或提交任意 SQL；
- Text-to-SQL 仅开放给管理员智能数据分析页面，并在独立权限校验后执行；
- 数据库 Agent 只接受一条 `SELECT`，禁止 `INSERT`、`UPDATE`、`DELETE`、`DROP`、`ALTER`、注释、存储过程和多语句；
- SQL 必须通过语法解析、表与字段白名单校验，不以简单关键词匹配作为唯一安全措施；
- 后端限制最大返回行数和查询超时，使用只读账号或只读数据源执行；
- 记录原始问题、生成 SQL、执行耗时、返回行数、结果状态和失败原因，审计日志不得记录敏感结果全文；
- 引用内容和工具结果视为不可信输入，防范文档 Prompt Injection；
- 管理接口进行角色校验，文档下载校验访问权限。

### 13.2 可靠性

- AI 调用具备超时、限流、异常降级和友好错误信息；
- 文档处理采用状态机，失败后可查看原因并重试；
- Redis 不可用时允许有限降级；
- 模型未配置时，非 AI 管理页面仍可启动和访问。

### 13.3 可观测性

- 记录请求场景、模型、耗时、Token、状态和降级原因；
- 记录检索策略、TopK、最高得分、引用数量和最终可信等级；
- 记录管理员 Text-to-SQL 的问题、生成 SQL、校验结果、执行耗时、返回行数和结果状态；
- 日志中不记录密码、API Key 和完整敏感文档。

### 13.4 可测试性

- 准备一套虚构软件企业样例数据；
- 建立固定问题集及期望引用文档；
- 对路由、检索、权限、工具安全和降级逻辑进行自动化测试；
- AI 结果不只断言全文，而是校验结构、引用和关键事实。

## 16. 初步验收标准

1. 项目能够按照文档在本地独立启动，核心页面可访问。
2. 管理员能够上传至少 PDF、DOCX、Markdown、TXT 四类文档并查看处理状态。
3. 用户能够针对已发布文档进行多轮流式问答。
4. 每个知识回答至少返回答案、可信等级和可点击引用；证据不足时明确拒绝猜测。
5. 系统能够比较两个文档版本并输出结构化差异。
6. 故障诊断能够组合至少两个只读工具与 RAG 结果生成排查清单。
7. 点踩或低可信问题能够进入知识缺口列表，并可被管理员处理。
8. AI 请求具备限流、超时、降级、日志和 Token 统计。
9. 普通用户只能通过预定义只读工具查询业务数据，无法提交或触发自由 SQL。
10. 管理员能够用自然语言生成并执行一条通过安全审核的 `SELECT`，页面展示生成 SQL、查询数据和分析结论；越权表、危险语句及多语句必须被拒绝并留有审计记录。
11. Redis 保存活跃会话记忆，H2 保存核心业务数据，职责边界清晰。
12. 通过固定测试问题集记录检索效果和回答依据，不使用无法验证的性能宣传。

## 17. 简历价值与可量化指标

项目完成后，简历重点应围绕“Spring AI 综合能力 + 企业知识业务闭环 + 工程治理”展开。可记录但必须经过实际测试的指标包括：

- 支持的文档格式、文档数量和切分片段数量；
- 固定测试集上的检索命中率、引用正确率和拒答准确率；
- 向量检索与混合检索的效果对比；
- Redis 缓存前后的响应耗时变化；
- 流式回答首段响应时间；
- Tool Calling 成功率和错误降级覆盖率；
- Text-to-SQL 生成成功率、安全拦截覆盖率和查询执行成功率；

不应在未测试前使用“高并发”“海量知识”“生产级准确率”等表述。项目的企业级特征主要体现为权限、版本、证据、审计、治理、降级和可观测性。

## 18. 风险与控制

| 风险 | 影响 | 控制方式 |
|---|---|---|
| 功能范围过大 | 无法在 9 月 14 日前形成稳定演示 | 9 月 10 日冻结功能；三个创新点只做最小闭环；砍掉语音、文生图、翻译、Ollama 和 PGvector 实现 |
| 模型输出不稳定 | 演示结果波动 | 结构化输出、低温度、规则校验、固定测试集 |
| RAG 命中但依据过期 | 给出错误操作建议 | 文档版本、状态和生效时间过滤 |
| 模型无依据编造 | 降低可信度 | 证据阈值、引用校验、明确拒答 |
| 自然语言 SQL 越权 | 数据安全风险 | 仅管理员可用、SQL AST 校验、表字段白名单、单条 SELECT、只读数据源、行数与超时限制、完整审计 |
| Redis 或模型不可用 | 核心流程失败 | 明确依赖状态、降级策略和友好提示 |
| 前置案例强行堆叠 | 产品主线混乱 | 核心能力业务化，展示型能力放入 P2 |

## 19. 已确认决策与待讨论事项

以下技术与范围决策已经确认：

1. 前端采用 Vue 3 + Vite + TypeScript。
2. 首版使用 SimpleVectorStore；保留向量存储抽象接口，但不实现 PGvector。
3. 默认使用 H2 文件数据库以保证独立演示，额外提供 MySQL 配置档。
4. 故障辅助诊断、版本对比、知识缺口雷达均为必做创新功能，但只实现稳定的最小业务闭环。
5. 普通用户采用受控 Tool Calling；管理员智能分析采用安全受限的 Text-to-SQL。
6. 文生图、语音和翻译不进入实现与最终演示，仅保留扩展可能。
7. 不接入 Ollama 本地模型。
8. 项目定位为“以 AI 应用开发为重点、以 Java 后端工程能力为基础”，两者结合而非互斥。
9. 2026 年 9 月 10 日冻结功能，9 月 14 日上午完成汇报。

当前仅剩一项待讨论事项：虚拟企业的行业、名称、业务背景及示例服务是否符合最终演示故事。“星云科技”只是此前用于避免真实企业数据的临时设定，并非来自真实公司或既有要求。

## 20. 当前建议结论

- 主题确认：面向中型软件企业的研发与 IT 运维知识运营助手。
- 核心主线：多格式知识入库 → 混合检索 → 可追溯 RAG → Tool Calling → 反馈闭环。
- 三个主要创新点：可信回答协议、文档版本与冲突感知、知识缺口雷达。
- 主要技术亮点：Spring AI ChatClient、Prompt、结构化输出、RAG、VectorStore、Tool Calling、ChatMemory、SSE 和 AI 接口治理。
- 数据库能力边界确认：普通用户业务查询采用受控 Tool Calling；管理员智能分析保留安全受限的 Text-to-SQL，由后端审核后通过只读数据源执行。
- 实施策略：优先完成 P0 闭环，再完成三个最小化 P1 创新闭环；语音、文生图、翻译和 Ollama 本次不纳入。
- 技术选型确认：Vue 3 + TypeScript；SimpleVectorStore；H2 默认配置并额外提供 MySQL 配置；使用本机 Redis；不接入 Ollama。
- 项目包装方向：以 AI 应用开发为重点，同时体现 Java 后端的接口设计、权限、安全、数据访问、缓存、日志、测试和工程治理能力。
- 进度约束：9 月 10 日功能冻结，9 月 11～13 日完成测试与汇报准备，9 月 14 日上午汇报。
- 下一步进入精简 PRD 和开发，不再继续扩展功能清单。
