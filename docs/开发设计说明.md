# OpsNexus 开发设计说明

> 版本：v1.1（开发边界修订）  
> 编写日期：2026 年 9 月 5 日  
> 依据：《项目策划书》《产品需求文档-PRD》  
> 目标：在 9 月 10 日功能冻结前完成可运行、可测试、可演示的最小稳定闭环

## 1. 开发原则

1. 以 OpsNexus 业务闭环为主，前置案例只在对应能力实现时参考，不逐项复现。
2. 使用前后端分离的模块化单体，不拆微服务。
3. H2 文件数据库是开发、测试和演示的验收基准；MySQL 只提供 Profile 和初始化方案。
4. AI 输出必须经过后端结构化封装和业务校验，前端不直接依赖模型原始文本格式。
5. 三个创新功能只实现一个固定场景的最小闭环。
6. 9 月 10 日后不增加实体、页面或核心接口。

## 2. 系统结构

```text
Vue 3 前端
   │ HTTP / SSE
   ▼
Spring Boot 单体应用
   ├─ auth          登录、JWT、角色校验
   ├─ knowledge     知识库、文档与版本
   ├─ ingestion     解析、切分、向量入库
   ├─ retrieval     检索、过滤与可信度计算
   ├─ assistant     问答、路由与 SSE
   ├─ diagnosis     故障诊断编排
   ├─ tool          预定义只读业务工具
   ├─ analytics     管理员 Text-to-SQL
   ├─ conversation  会话、消息、引用、反馈
   ├─ gap           知识缺口聚合与处理
   └─ governance    AI 日志、超时、Token 与异常处理
        │
        ├─ H2 文件数据库（业务与审计数据）
        ├─ Redis（活跃会话上下文与短期计数）
        ├─ SimpleVectorStore（文档片段向量）
        └─ 本地文件目录（原始文档）
```

## 3. 后端工程约定

建议根包名为 `com.opsnexus`，每个业务模块内部按 `controller`、`service`、`repository`、`domain`、`dto` 划分。跨模块只通过 service 或明确的接口调用，不直接访问其他模块的 repository。

统一约定：

- 普通 JSON 接口返回 `ApiResponse<T>`，包含 `code`、`message`、`data`、`requestId`。
- 分页返回 `PageResult<T>`，包含 `items`、`page`、`size`、`total`。
- 时间统一使用 ISO 8601，并由后端按数据库时区保存。
- 主键使用数据库自增 `BIGINT`；业务状态使用字符串枚举。
- 密码使用 BCrypt，不保存明文。
- API Key 只从环境变量读取，不写入仓库和响应。
- 业务异常由全局异常处理器转换为稳定错误码。

首版认证采用 Spring Security + JWT。只提供登录，不实现注册、找回密码、刷新令牌和第三方登录。初始化一个管理员和一个普通用户演示账号。

#### `document_version`

| 字段 | 类型 | 约束/说明 |
|---|---|---|

| version_no | VARCHAR(30) | 如 `v1.0` |

```text

                                  └→ FAILED → PROCESSING
发布：DRAFT → PUBLISHED → ARCHIVED
```

## 6. 关键业务实现

### 6.1 文档入库

1. 校验管理员权限、文件类型、20 MB 大小限制和空文件。
2. 生成服务器文件名与 SHA-256，不使用原始文件名拼接路径。
3. 按格式解析；PDF 保留页码，扫描件不做 OCR。解析失败拒绝上传。
4. 写入版本与片段正文，发布状态为 `DRAFT`，处理状态为 `PARSED`；管理员触发向量化后才进入 `PROCESSING`。
5. 使用统一切分策略生成片段，写入 SimpleVectorStore。
6. 保存向量 ID 与版本关系；全部成功后进入 `READY`。
7. 任一步失败则清理本次已写入向量并标记 `FAILED`。
8. 只有 `READY`、向量落盘成功且已到生效时间的版本可发布。锁定逻辑文档记录，在一个数据库事务内归档旧版本、发布新版本并切换 current_version_id。归档当前版本时清空该指针，不自动恢复旧版本；首版无预约发布。

首版按单实例设计，向量写入串行化。每个片段用版本 ID 和片段序号产生稳定 vector_id；先记录本次片段关联，再写入向量并保存同目录临时快照，通过原子替换提交文件，成功后才标记 READY。不能原子替换时按失败处理，保留旧快照。

H2 与向量文件不共享事务，采用状态和补偿恢复：启动先加载快照，残留 PROCESSING 标记 FAILED；重试按已记录的 vector_id 清理后重新入库。启动核对 READY 版本的向量完整性，缺失或文件损坏时禁用受影响检索并提示重建，不能静默使用残缺数据。草稿删除先标记不可检索、清理向量并落盘，成功后删除片段关联和原文件；清理失败保留记录供重试。所有入库、重建和删除使用同一写锁。

### 6.2 RAG 与可信回答

首版固定流程：读取最近会话上下文 → 检索已发布当前版本 → 生成带证据回答 → 后端计算可信等级 → 保存消息与引用 → 触发缺口判定。

候选进入模型前按 H2 核对知识库启用状态、权限、process_status=READY、publish_status=PUBLISHED、生效时间和 current_version_id；过滤后不足时可扩大候选检索一次，仍无有效证据则拒答，不回退旧版本。

可信度先对重复片段去重，再综合问题与证据的相关程度、检索得分、版本有效性和已知冲突。引用必须指向实际召回片段；一个直接支持问题的片段也可判高，多个重复片段不能抬高等级。后端规则不声称能完整证明语义正确性，对问题覆盖不明的结果最高判中，阈值通过固定问题集校准。页面同时展示证据充分性与理由，不以百分比冒充准确率。

OPS-V2-001 的多轮上下文以关系库为长期事实源，使用 Redis 作为 `opsnexus:conversation:{userId}:{conversationId}:recent` 的近期缓存。默认 TTL 为 30 分钟，保留最近 8 条已完成消息、最多 4,000 字符，优先保留最新消息；删除会话时主动失效。缓存 miss 从 `conversation + chat_message` 按 userId 与 conversationId 读取并回填；Redis 不可用时直接执行同一数据库读取，不影响聊天主链路。只有 USER 和已持久化完成的 ASSISTANT 消息进入上下文，未完成/失败助手输出不进入。

模型输入保持边界：system instruction（其中以数据区包裹当前检索 evidence）→ 历史 `user`/`assistant` message roles → 当前 `user` question。历史和检索 evidence 都被标记为不可信数据，不能覆盖 system instruction；历史只用于理解指代和主题，企业事实仍须由当前授权、当前版本的 retrieval evidence 支撑。SSE `complete` 可返回 `contextTurnsUsed` 与 `approximateContextChars` 供调试，但前端不展示给普通用户；不新增数据库字段或记录对话正文。

### 6.3 受控 Tool Calling

普通用户只允许调用参数化工具：

- `getServiceInfo(serviceName)`；
- `getRecentReleases(serviceName, limit)`；
- `findSimilarIncidents(serviceName, symptom, limit)`。

工具内部调用业务 service/repository，不接收 SQL，不返回无关字段，不执行写操作。故障诊断必须至少组合其中两个工具和 RAG 证据。

诊断证据卡从引用和工具结果直接组装：SOP 名称/版本、服务版本、最近发布时间、工具 queriedAt、成功或失败状态。快照保存于消息 evidence_snapshot，追问和历史展示可复查；缺失字段显示“未获取”，AI 建议不得混入事实字段。

### 6.4 文档版本对比

只允许同一 `document_id` 下的两个版本。后端抽取两侧关键片段，要求模型返回固定 DTO：`additions`、`deletions`、`changes`、`risks`、`conflicts`、`recommendedVersion`、`coverageNote`。解析失败时允许一次结构化重试，仍失败则返回明确错误。

### 6.5 知识缺口

无命中、低分、证据不足、冲突和点踩均可触发。问题先去除多余空白并统一大小写，再生成向量与未关闭缺口比较；高于配置阈值则追加 occurrence，否则新建。关闭缺口不删除历史记录。

重新验证接口使用同一知识库和原问题执行当前版本检索，返回证据、得分、版本、验证时间与新增引用，保存最近结果；不再次触发缺口计数，也不自动关闭。管理员根据证据填写 resolution_note 后关闭，验证未命中仍显示待处理；人工特殊关闭须记录原因且不标记验证通过。

### 6.6 Text-to-SQL

1. Spring Security 校验 `ADMIN`。
2. Prompt 只暴露三张白名单表的字段、关系和 H2 方言。
3. 模型只生成 SQL，不负责决定是否安全。
4. SQL 解析为 AST；只接受单条 SELECT。
5. 递归校验访问的表、字段、函数、JOIN、排序和子结构。
6. 禁止系统表、CTE、UNION、子查询、存储过程及非白名单函数；最多两个 JOIN，必须使用 service_id 到 service_catalog.id 的白名单关联条件，拒绝 CROSS JOIN、无关联条件和不支持的 AST 节点。
7. 后端强制最大 100 行和 3 秒查询超时。
8. 查询数据源使用独立非管理员账号，仅授予三张白名单表 SELECT 权限；连接只读标记仅作补充。初始化/业务账号不进入模型查询执行器。启动检查授权配置，不对真实业务表试写；在隔离测试库验证写入、建表和读取非授权业务表均被拒绝。
9. 业务数据源先写审计，再执行查询并更新结果状态；审计不可用则拒绝查询。模型结果解读失败时仍返回真实表格并提示解读失败，不能伪造结论。两类数据源独立注入，SQL 执行器不得获取业务数据源。

原案例 16 的字符串前缀、危险词和分号检查只能作为补充防线，不能代替 AST 校验。

## 8. 配置与存储目录

建议 Profile：

- `dev`：H2 文件数据库、本机 Redis、真实云端模型；
- `test`：独立 H2 测试文件或临时数据库、可替换模型客户端；
- `mysql`：MySQL 业务库配置示例，不作为现场演示默认值。

运行数据统一放在项目可配置目录，例如：

```text
runtime/
  db/          H2 文件
  uploads/     原始文档
  vectors/     SimpleVectorStore 持久化文件
  logs/        应用日志
```

`runtime/`、环境变量文件、IDE 文件和构建产物应加入 `.gitignore`。
